# 故事银行（STAR + R）

> **用途**：积累面试用 STAR+R 故事。每次面试准备从这里匹配故事；每次面试后把反馈写回，越用越强。
> **数据来源**：故事事实层取自 `references/project-library.md`（弹药库），口述版为面试打磨后的表达。
> **约束**：所有故事必须基于真实项目；数据必须与弹药库一致，禁止夸大。
> **维护**：新增故事用下方模板；面试后按 §复盘流程 回写反馈。
> ⚠️ 本文件为示例骨架，故事列表初始为空，随使用累积。

## 故事结构

| 字段 | 含义 |
|------|------|
| S 背景 | 项目目标、业务场景、约束条件 |
| T 挑战 | 具体要解决的核心问题 |
| A 行动 | 3 个关键动作（按逻辑顺序） |
| R 结果 | 量化数据 + 业务影响（取自弹药库 Result） |
| +R 反思 | 学到的经验 / 可复用方法 / 若重来的改进 |

## 复盘流程（面试后执行）

**触发**：面试结束后，用户说"面试复盘/面试反馈"，或直接给出面试官的问题。

**核心分工**：
- **面试官的问题** → 归入 `interview-question-bank.md`（问题库，按岗位类型分层）
- **故事本身的改进** → 回写本文件

**执行**：
1. **收问题**：用户提供面试官的问题（必）；临场回答与自评（可选，有则更佳）
2. **问题处理**：按问题库 §6 流程归档→评估→改进→反哺（产出落在问题库）
3. **故事回写**（仅当该故事被实际用到）：
   - 在「面试使用记录」表追加一行（哪个 JD 用到、被追问什么）
   - 追问暴露的不足 → 补进 **+R 反思**
4. **新增故事**：面试中出现值得沉淀的新案例 → 用模板创建

**注意**：不强求"效果评分"——面试官未必问到该故事；有实际使用记录就记，没有就留空。

## 与选材的对接（每次面试准备时）

**匹配流程**：
1. Step 2 先从本库匹配与本次选中项目对应的故事
2. **匹配失败兜底**（库内故事少是常态）：从弹药库选中项目现构故事（按 `interview-self-intro.md` §3 打磨口述版）
3. **入库（双轨）**：
   - **准备后**：本次现构的口述版，**经用户确认质量 OK** → 存入库（作为该项目的标准口述版）
   - **复盘后**：实际用到的故事 → 更新使用记录与反思

> 双轨的目的：让库随服务过的 JD 逐步变厚——否则库内只有预置故事，后续每份面试准备都走"现构"，复用无从谈起。

**库内故事与弹药库的关系**：弹药库 = 事实层（唯一数据源）；本库 = 表达层（口述版 + 实战记录）。本库数据与弹药库不一致时，**以弹药库为准**。

## 维护说明

- **加故事**：用 §故事模板 追加到「故事列表」；事实层必须来自弹药库，数据一致。
- **改故事**：直接编辑对应条目；数据变更需同步核对弹药库。
- **故事与弹药库的关系**：弹药库 = 事实层（原始素材）；故事银行 = 表达层（面试打磨后的口述版 + 反馈沉淀）。同一项目可在两处存在，但**数据必须一致**。
